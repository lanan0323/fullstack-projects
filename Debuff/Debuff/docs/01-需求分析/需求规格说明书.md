## 1. 引言

### 1.1 编写目的

本文档是"Debuff 饰品交易系统"项目需求分析阶段的正式产出物，用于明确系统的建设背景、业务范围、功能需求与非功能需求，作为后续系统设计、编码实现、测试验收等阶段的工作依据。本文档面向项目组成员、指导老师及答辩评审人员。

### 1.2 项目背景

随着电子竞技产业的快速发展，以《反恐精英 2》(CS2) 为代表的射击游戏在全球拥有庞大的玩家群体。游戏内的武器饰品（皮肤、手套、刀具等）因具备稀缺性、观赏性与保值属性，逐渐形成了活跃的交易市场。

然而，主流第三方交易平台通常存在以下问题：

1. **交易流程不透明**：买家与卖家之间缺乏清晰的订单状态跟踪；
2. **资金安全难以保障**：缺乏可靠的资金托管与冻结机制；
3. **手续费不透明**：平台抽成规则不清晰，卖家实收金额不直观；
4. **信息分散**：饰品价格走势、磨损度、检视信息等缺乏统一展示。

本项目旨在构建一个面向高校实训场景的 CS2 饰品交易平台——**Debuff**，覆盖饰品浏览、发布出售、下单购买、资金托管、订单管理、后台运营等完整业务闭环，实现饰品交易的全流程线上化与规范化管理。

### 1.3 术语定义

| 术语 | 说明 |
| --- | --- |
| 饰品（Skin） | CS2 游戏内可交易的武器外观道具，包含武器类型、品质、磨损度等属性 |
| 磨损度（Float Value） | 饰品的磨损程度数值，取值范围 0.00~1.00，分为崭新出厂、略有磨损、久经沙场、破损不堪、战痕累累五档 |
| 挂牌（Listing） | 卖家将库存饰品以指定价格挂出待售的记录 |
| 冻结（Frozen） | 交易过程中买家资金被平台托管锁定、饰品库存被锁定的状态 |
| 平台手续费 | 交易成交后平台按成交价一定比例抽取的服务费用 |
| 求购（Buy Order） | 买家发布的以指定价格收购指定饰品的意向订单 |
| 模拟支付 | 实训环境中以模拟方式完成充值/提现的资金流转 |

## 2. 项目概述

### 2.1 项目目标

1. 构建功能完整的 CS2 饰品交易平台，覆盖"用户注册登录 → 饰品浏览 → 下单购买 → 确认收货 / 自动取消 → 资金结算"的完整交易闭环；
2. 提供安全可靠的资金托管机制，交易期间买家资金冻结、饰品锁定，保障买卖双方权益；
3. 提供管理端运营平台，支持饰品、订单、钱包、公告等业务数据的统一管理；
4. 提供数据看板，为运营决策提供数据支撑；
5. 系统具备良好的扩展性与可维护性，为后续功能迭代预留空间。

### 2.2 用户特征

| 用户类型 | 特征描述 |
| --- | --- |
| 普通用户（买家/卖家） | 平台交易的主要参与者，可浏览市场、购买饰品、发布出售、管理钱包；不需要专业计算机知识，要求界面友好、流程清晰 |
| 管理员 | 平台运营人员，负责饰品目录、交易订单、钱包资金、公告内容的日常管理，需要数据统计支持 |
| 系统管理员 | 负责系统用户、角色、菜单、字典等基础配置的维护 |

### 2.3 运行环境

| 类别 | 要求 |
| --- | --- |
| 操作系统 | Windows / Linux（服务器端） |
| 后端运行环境 | JDK 1.8+，Spring Boot 2.5.15 |
| 数据库 | MySQL 8.0，Redis 5.0+ |
| 前端运行环境 | Node.js 16+，Vue 3 / Vite 5 |
| 浏览器 | Chrome / Edge 等现代浏览器 |

### 2.4 假设与约束

1. 系统用于高校实训/毕设场景，资金流转采用**模拟支付**方式，不接入真实支付渠道；
2. 交易手续费率、订单超时时间等业务参数支持配置文件调整；
3. 系统为单体应用架构（前后端分离），不涉及微服务拆分；
4. 饰品为系统预置的静态数据，不与游戏官方接口进行实时对接。

## 3. 可行性分析

### 3.1 技术可行性

系统采用成熟的 RuoYi-Vue（若依）前后端分离框架作为基础，后端基于 Spring Boot 2.5.15 + MyBatis + MySQL + Redis，前端基于 Vue 3 + Element Plus + Vite，均为当前主流且稳定的技术栈；核心交易逻辑（资金冻结、库存流转）由团队自主开发，逻辑清晰、可控性强。团队已具备相应技术基础，技术可行性高。

### 3.2 经济可行性

系统开发使用开源框架与技术栈，无软件采购成本；部署环境为实验室/本地服务器，无需额外硬件投入；系统运行维护成本低。经济上完全可行。

### 3.3 操作可行性

系统提供图形化界面，普通用户经过简单引导即可完成注册、购买、出售等操作；管理端提供标准化的表格管理界面，操作路径清晰；系统对关键操作（购买、取消等）提供明确的状态反馈与错误提示。操作可行性高。

### 3.4 法律可行性

系统为教学实训项目，不涉及真实资金交易与第三方支付接口；饰品数据为预置演示数据，不侵犯游戏厂商权益；符合相关法律法规要求。

## 4. 业务流程分析

### 4.1 总体业务流程

```
┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
│ 用户注册 │ → │ 充值/获取 │ → │ 浏览市场 │ → │ 下单购买 │ → │ 确认收货 │
│ 登录    │   │ 饰品/资金 │   │ 选择饰品 │   │ 资金冻结 │   │ 资金结算 │
└────────┘   └────────┘   └────────┘   └────────┘   └────────┘
                                    │
                                    └─ 超时未确认 → 自动取消 → 资金退回/饰品解冻
```

### 4.2 购买业务流程（核心）

1. 买家浏览饰品市场，查看饰品详情（基本信息、在售列表、价格走势）；
2. 买家选择在售挂牌，确认价格后发起购买；
3. 系统校验买家余额充足后，冻结买家资金（含平台手续费），锁定饰品库存，生成订单（状态：待确认）；
4. 买家在订单详情中确认收货；
5. 系统向卖家账户结算（成交价 - 平台手续费），登记双方资金流水，订单状态置为已完成；
6. 若买家在超时时间（默认 15 分钟，可配置）内未确认收货，定时任务自动取消订单：买家资金解冻退回，饰品恢复在售状态。

### 4.3 出售业务流程

1. 卖家在"我的库存"中选择在库饰品，填写出售价格发布挂牌；
2. 挂牌后饰品状态变为"在售"，出现在市场列表中；
3. 挂牌被买家购买后饰品状态变为"冻结"，交易完成后转入买家库存；
4. 卖家可随时对"在售"状态的挂牌执行下架操作，饰品退回库存。

### 4.4 资金业务流程

1. 用户通过模拟支付进行账户充值，余额增加并生成充值流水；
2. 购买饰品时，买家余额按成交价+手续费冻结；
3. 确认收货后，冻结资金解冻并划转：平台手续费入平台账户，其余入卖家余额；
4. 订单取消时，冻结资金全额退回买家余额；
5. 用户可发起提现（模拟），余额扣减并生成提现流水。

## 5. 系统功能需求

### 5.1 系统角色与总体功能结构

系统包含两类角色：

| 角色 | 职责 |
| --- | --- |
| 普通用户 | 使用平台全部前台功能：市场、库存、交易、钱包、个人中心 |
| 管理员 | 使用管理端功能：系统管理、饰品管理、交易管理、公告管理、数据看板 |

总体功能结构：

```
Debuff 饰品交易系统
├── 前台用户端（Web 浏览器）
│   ├── 用户模块：注册、登录、个人中心（资料修改、密码修改）
│   ├── 市场模块：饰品浏览、搜索、筛选、排序、详情、价格走势
│   ├── 收藏模块：收藏/取消收藏、我的收藏
│   ├── 库存模块：我的库存、库存详情、库存修改
│   ├── 出售模块：上架挂牌、下架
│   ├── 交易模块：下单购买、确认收货、取消订单、我的交易
│   ├── 求购模块：发布求购、取消求购、改价、我的求购
│   ├── 钱包模块：余额查询、充值、提现、资金流水
│   └── 公告模块：最新公告展示
└── 管理端
    ├── 系统管理：用户、角色、菜单、字典、参数
    ├── 饰品管理：饰品定义、武器类型、饰品品质、上下架
    ├── 交易管理：订单管理、钱包管理、钱包流水管理
    ├── 公告管理：公告发布、编辑、删除、导出
    └── 数据看板：运营总览、交易趋势、订单分布、成交排行
```

## 6. 非功能需求

### 6.1 性能需求

| 指标 | 要求 |
| --- | --- |
| 页面响应时间 | 普通页面响应时间 ≤ 2 秒，列表页 ≤ 3 秒 |
| 接口平均响应时间 | 普通查询接口 ≤ 500ms，交易类接口（下单/确认/取消）≤ 1 秒 |
| 并发支持 | 支持 100 个并发用户正常访问，交易接口无超卖/资金不一致问题 |
| 定时任务 | 订单超时扫描任务每 60 秒执行一次，单次扫描 ≤ 5 秒 |

### 6.2 安全需求

1. 认证安全：采用 JWT 无状态令牌认证，令牌有效期 30 分钟，支持续期；登录需图形验证码；
2. 授权安全：管理端接口基于 RBAC 权限模型控制，普通用户无法访问管理端资源；
3. 数据安全：密码采用 BCrypt 加密存储；关键资金操作（下单、确认、取消、充值、提现）记录资金流水，变动前后余额可追溯；
4. 接口安全：前后端分离部署时，管理端接口不对外网暴露或配置访问白名单；
5. 防并发安全：下单/取消等关键操作采用条件更新（状态校验）兜底，防止并发竞态导致资金不一致。

### 6.3 可靠性需求

1. 交易数据强一致：资金冻结、库存锁定、订单创建在同一事务中完成，任一失败全部回滚；
2. 超时自动取消任务保证幂等：订单取消后状态不再回退，重复扫描不重复处理；
3. 数据库每日备份（实训环境每周备份），日志保留 30 天。

### 6.4 易用性需求

1. 前台采用深色主题，贴近 CS2 游戏风格，界面风格统一；
2. 关键操作提供明确的成功/失败提示与原因说明（如"余额不足"）；
3. 空数据页面提供引导提示（如"暂无库存，去市场逛逛"）；
4. 管理端沿用若依标准布局，降低学习成本。

### 6.5 可维护性需求

1. 后端按模块分层（controller/service/mapper），业务模块独立（debuff-trade 模块承载全部核心业务）；
2. 业务参数（订单超时时间、手续费率）支持配置文件修改；
3. 代码统一规范，关键业务逻辑注释完整；
4. 提供完整 SQL 初始化脚本，环境可一键重建。

### 6.6 兼容性需求

1. 浏览器兼容 Chrome 80+、Edge 80+、Firefox 78+；
2. 分辨率适配 1366×768 及以上。

## 7. 数据需求概述

系统核心数据实体包括：用户（sys_user / debuff_user）、饰品（debuff_skin）、武器类型（debuff_weapon_type）、饰品品质（debuff_skin_quality）、库存（debuff_inventory）、挂牌（debuff_skin_listing）、订单（debuff_order）、钱包（debuff_user_wallet）、资金流水（debuff_wallet_log）、价格历史（debuff_price_history）、求购（debuff_buy_order）、收藏（debuff_favorite）、公告（debuff_announcement）等。

数据实体间核心关系：

- 用户 1:N 库存（用户持有多个饰品库存）；
- 用户 1:N 挂牌（卖家发布多个挂牌）；
- 用户 1:N 订单（买家/卖家参与多个订单）；
- 用户 1:1 钱包；
- 钱包 1:N 资金流水；
- 饰品 1:N 库存 / 挂牌 / 价格历史 / 求购；
- 挂牌 1:1 订单（一个挂牌被购买生成一笔订单）。

详细表结构见《数据库设计文档》。
