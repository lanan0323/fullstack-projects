## 1 项目概述

### 1.1 项目背景

随着《反恐精英2》（Counter-Strike 2，简称CS2，前身为CS:GO）在全球范围内的持续流行，游戏饰品文化已形成庞大的虚拟经济生态。CS2中的武器皮肤、手套、刀具等饰品因其稀缺性和观赏性，产生了真实的市场交易需求。目前市面上的饰品交易平台（如网易BUFF、C5GAME、IGXE等）虽然功能成熟，但存在手续费偏高、用户体验参差不齐等问题，且其商业闭源特性使得学术研究和个人学习难以深入理解其业务逻辑。

本项目旨在设计并实现一个名为 **Debuff** 的CS2饰品交易平台，作为计算机相关专业毕业设计项目。平台模拟真实饰品交易场景，涵盖饰品浏览、收藏、上架、购买、求购、钱包、订单管理等核心业务流程，为用户提供完整的虚拟饰品交易体验。项目基于若依(RuoYi-Vue)前后端分离框架进行二次开发，在保证系统稳定性的同时，充分锻炼团队的Java后端开发与Vue前端开发能力。

### 1.2 项目目标

本项目的核心目标包括：

1. **构建完整的饰品交易闭环**：实现从饰品上架、市场浏览、下单购买到确认收货的全流程交易功能，模拟真实饰品交易平台的业务逻辑。
2. **提供丰富的市场信息展示**：支持饰品分类筛选、关键词搜索、价格历史图表、热门推荐等功能，帮助用户快速定位目标饰品。
3. **实现安全的交易保障机制**：通过订单超时自动取消、资金冻结/解冻、余额校验等机制，确保交易过程的安全可靠。
4. **支持求购撮合功能**：允许用户发布求购意向，为买卖双方提供多元化的交易撮合方式。
5. **提供完善的后台管理功能**：包括数据看板、订单管理、钱包管理、公告管理等，方便运营人员日常运维。
6. **遵循软件工程规范**：按照标准的软件开发流程进行需求分析、设计、编码、测试，产出规范的工程文档。

### 1.3 项目范围

本系统的范围涵盖以下内容：

- **用户端（前台）**：面向普通用户，提供饰品浏览、收藏、库存管理、上架/下架、购买交易、求购发布、钱包充值/提现、公告查看、个人信息管理等功能。
- **管理端（后台）**：面向管理员，提供饰品管理、订单管理、钱包管理、公告管理、数据看板、系统管理（用户/角色/菜单/字典/日志/定时任务）等功能。

本系统不涉及以下内容：

- 真实支付对接（采用模拟支付机制）
- 与Steam平台的实际API对接（饰品数据为手动录入或模拟数据）
- 饰品实际交割（不涉及Steam交易报价）
- 用户实名认证与防沉迷系统

## 2 系统总体描述

### 2.1 系统架构概述

Debuff平台采用 **前后端分离** 的B/S（Browser/Server）架构，整体分为三层：

- **表现层（前端）**：基于Vue3框架构建单页面应用（SPA），通过Element Plus组件库实现界面设计，使用Vite作为构建工具，通过ECharts实现数据可视化图表。前端通过HTTP RESTful API与后端通信，使用JWT进行身份认证。
- **业务逻辑层（后端）**：基于Spring Boot框架构建RESTful服务，使用MyBatis作为持久层框架操作MySQL数据库，通过Redis实现缓存管理和会话管理。后端遵循若依框架的标准分层架构（Controller → Service → Mapper）。
- **数据层**：使用MySQL 8.0关系型数据库存储业务数据，Redis用于缓存热点数据（如饰品列表、用户会话等）以及定时任务锁。

## 3 用户角色分析

### 3.1 角色定义

本系统定义以下两类核心角色：

#### 3.1.1 普通用户（User）

普通用户是平台的主要使用者，即CS2饰品的买家和卖家。一个普通用户可以同时扮演买家和卖家两种身份——既可以浏览市场购买他人上架的饰品，也可以将自己的饰品上架出售。

**主要特征：**
- 通过注册获得平台账户
- 拥有个人钱包，可进行充值和提现
- 拥有个人库存，可管理自己的饰品
- 可在市场上架/下架饰品、下单购买、发布求购
- 可查看系统公告和个人交易记录

#### 3.1.2 管理员（Admin）

管理员是平台的运营维护人员，负责平台日常运营管理。管理员通过后台管理系统进行操作，不直接参与饰品交易。

**主要特征：**
- 由系统超级管理员创建或分配
- 负责饰品基础数据维护（武器类型、品质、饰品信息）
- 负责订单监控与管理
- 负责用户钱包监控
- 负责发布系统公告
- 通过数据看板了解平台运营状况
- 管理系统用户、角色、权限等

#### 3.1.3 超级管理员（Super Admin）

超级管理员是系统的最高权限角色（若依框架内置），拥有系统全部权限，主要负责系统级配置和其他管理员的创建与管理。在毕业设计场景中，超级管理员通常由组长或指导教师担任。

#### UC-07 下单购买

| 项目 | 描述 |
|------|------|
| **用例名称** | 下单购买饰品 |
| **参与者** | 普通用户 |
| **前置条件** | 用户已登录系统，用户不是该饰品的卖家，用户钱包余额充足 |
| **后置条件** | 订单创建成功，买家资金被冻结，饰品状态变为"锁定" |
| **基本流程** | 1. 用户在饰品详情页或市场列表点击"购买"按钮<br>2. 系统弹出订单确认对话框，显示饰品信息、售价、当前余额<br>3. 用户确认购买<br>4. 系统校验：买家不能是卖家本人、钱包余额 >= 售价、饰品仍在售<br>5. 系统创建订单，状态为"待付款/待发货"<br>6. 系统冻结买家钱包中对应金额<br>7. 系统将饰品状态标记为"锁定"（其他用户不可购买）<br>8. 系统启动15分钟超时计时器<br>9. 系统提示下单成功，跳转至订单详情 |
| **异常流程** | 4a. 余额不足，提示"余额不足，请先充值"<br>4b. 买家即卖家，提示"不能购买自己的饰品"<br>4c. 饰品已被他人购买，提示"该饰品已售出" |

### 5.4 订单交易模块

**模块编号**：MOD-04  
**所属角色**：成员A  
**模块概述**：订单交易模块是平台的核心业务模块，处理饰品的购买、支付、收货、取消等完整交易流程，并包含订单超时自动取消的定时任务机制。

#### 5.4.1 下单购买

**功能描述**：买家对在售饰品发起购买请求，创建交易订单。

**输入**：
- 饰品ID / 上架记录ID
- 买家ID（从Token获取）

**输出**：
- 订单创建结果，包含订单编号

**业务规则**：
- BR-44：买家不能购买自己上架的饰品
- BR-45：下单时校验买家钱包可用余额（余额 - 冻结金额）>= 售价
- BR-46：下单时校验饰品状态必须为"在售"且未被其他订单锁定
- BR-47：下单成功后执行以下原子操作：
  - 创建订单记录，状态为"待收货"
  - 冻结买家钱包中对应金额
  - 将饰品状态标记为"锁定"
  - 启动15分钟超时计时
- BR-48：订单编号生成规则：年月日时分秒 + 6位随机数（如 DD20250101120000 + 123456）
- BR-49：所有资金操作需使用数据库事务保证一致性

#### 5.4.2 确认收货

**功能描述**：买家确认收到饰品，完成交易。

**输入**：
- 订单ID
- 买家ID（从Token获取）

**输出**：
- 操作结果

**业务规则**：
- BR-50：仅订单创建者（买家）可确认收货
- BR-51：仅"待收货"状态的订单可确认收货
- BR-52：确认收货后执行以下操作：
  - 订单状态更新为"已完成"
  - 买家冻结金额正式扣除（余额减少）
  - 卖家钱包余额增加（收到货款）
  - 饰品所有权转移给买家（更新库存记录的所属用户）
  - 饰品状态恢复为"库存中"
- BR-53：交易完成后生成双方的流水记录

#### 5.4.3 取消订单

**功能描述**：买家主动取消未完成的订单。

**输入**：
- 订单ID
- 买家ID（从Token获取）

**输出**：
- 操作结果

**业务规则**：
- BR-54：仅订单创建者（买家）可取消订单
- BR-55：仅"待收货"状态的订单可取消
- BR-56：取消后执行以下操作：
  - 订单状态更新为"已取消"
  - 解冻买家冻结的对应金额
  - 饰品状态恢复为"在售"
- BR-57：取消操作需记录操作日志

#### 5.4.4 查看交易记录

**功能描述**：用户查看自己的历史订单列表。

**输入**：
- 用户ID（从Token获取）
- 分页参数
- 筛选条件（订单状态、时间范围，可选）

**输出**：
- 订单列表，每项包含：订单编号、饰品名称、饰品图片、售价、订单状态、创建时间、对方昵称（买家显示卖家，卖家显示买家）

**业务规则**：
- BR-58：用户可查看自己作为买家或卖家的所有订单
- BR-59：支持按订单状态筛选（全部/待收货/已完成/已取消/已超时）
- BR-60：订单列表按创建时间倒序排列

#### 5.4.5 订单超时自动取消

**功能描述**：系统定时任务自动取消超时未确认收货的订单。

**输入**：
- 定时任务触发（无外部输入）

**输出**：
- 超时订单取消处理结果

**业务规则**：
- BR-61：定时任务执行频率：每分钟执行一次
- BR-62：超时阈值：订单创建时间距今超过15分钟
- BR-63：仅处理状态为"待收货"的订单
- BR-64：超时取消逻辑与手动取消一致（BR-56）
- BR-65：超时取消后，订单状态标记为"已超时"（区别于主动取消的"已取消"）
- BR-66：定时任务需使用分布式锁（Redis），防止多实例重复执行

## 6 非功能需求

### 6.1 性能需求

| 编号 | 需求描述 | 指标要求 |
|------|---------|---------|
| NFR-01 | 页面响应时间 | 普通页面加载时间不超过3秒（首次加载），API接口响应时间不超过1秒 |
| NFR-02 | 并发处理能力 | 系统支持至少100个用户同时在线操作，核心接口（如下单）QPS不低于50 |
| NFR-03 | 数据库查询性能 | 单表查询响应时间不超过200ms，关联查询不超过500ms |
| NFR-04 | 缓存命中率 | 热点数据（饰品列表、字典数据）Redis缓存命中率不低于90% |
| NFR-05 | 前端渲染性能 | 列表页渲染100条数据无明显卡顿，ECharts图表渲染时间不超过1秒 |
| NFR-06 | 文件上传 | 图片上传（2MB以内）处理时间不超过5秒 |
| NFR-07 | 数据导出 | 导出1000条订单数据生成Excel文件时间不超过10秒 |

### 6.2 安全性需求

| 编号 | 需求描述 | 具体要求 |
|------|---------|---------|
| NFR-08 | 身份认证 | 采用JWT Token机制，Token有效期24小时，支持Token刷新 |
| NFR-09 | 密码安全 | 用户密码使用BCrypt算法加密存储，不可逆 |
| NFR-10 | 权限控制 | 基于RBAC模型实现菜单级和按钮级权限控制，使用Spring Security框架 |
| NFR-11 | SQL注入防护 | 使用MyBatis参数化查询，禁止拼接SQL字符串 |
| NFR-12 | XSS防护 | 富文本内容入库前进行XSS过滤，使用白名单机制 |
| NFR-13 | CSRF防护 | 基于JWT的无状态认证天然防御CSRF攻击 |
| NFR-14 | 接口安全 | 敏感操作接口（充值、提现、下单）需进行Token校验和权限校验 |
| NFR-15 | 数据隔离 | 用户只能访问自己的数据（库存、订单、钱包等），通过用户ID隔离 |
| NFR-16 | 资金安全 | 所有涉及资金变动的操作使用数据库事务（@Transactional），保证ACID特性 |
| NFR-17 | 并发安全 | 下单、充值、提现等操作使用数据库乐观锁或Redis分布式锁，防止并发导致数据不一致 |
| NFR-18 | 日志审计 | 关键业务操作（下单、充值、提现、上下架）记录操作日志，包含操作人、操作时间、IP地址、操作内容 |

| 编号 | 需求描述 | 具体要求 |
|------|---------|---------|

## 10 约束与假设

### 10.1 约束条件

1. **技术约束**：必须基于若依(RuoYi-Vue) 3.8.7框架进行二次开发，不得更换基础框架。
2. **时间约束**：作为毕业设计项目，需在规定的毕设周期内完成全部开发、测试和文档编写工作。
3. **人员约束**：四人团队协作开发，需合理分配任务，确保每人至少负责两个独立模块。
4. **功能约束**：系统为模拟交易平台，不涉及真实资金流转和真实饰品交割。
5. **部署约束**：系统需能在普通云服务器（2核4G配置）上正常运行。

### 10.2 假设条件

1. 所有团队成员具备Java、Vue.js基础开发能力。
2. 开发环境可正常访问互联网，用于下载依赖和查阅文档。
3. MySQL 8.0和Redis服务可在开发/部署环境中正常安装和运行。
4. 若依框架提供的标准功能模块（用户/角色/菜单/日志等）可直接使用，无需重新开发。
5. 测试数据（饰品信息、图片等）由团队成员手动准备。
6. 项目评审/答辩环境中可正常部署和演示系统。
