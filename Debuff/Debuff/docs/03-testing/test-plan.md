# 第一部分 测试方案

## 1. 测试目标

本测试方案旨在对 Debuff CS2饰品交易平台进行全面、系统的质量验证，确保系统满足需求规格说明书中定义的功能与非功能需求。具体目标如下：

1. **功能完整性验证**：确认所有业务模块（饰品市场、库存管理、上架/下架、交易订单、求购系统、钱包系统、收藏、公告、后台管理、数据看板）的功能均按照需求正确实现，覆盖正常流程与异常流程。
2. **数据一致性验证**：确保交易订单、钱包余额、库存状态等核心数据在并发操作和异常场景下保持一致，杜绝超卖、重复扣款、数据丢失等问题。
3. **接口可靠性验证**：验证前后端接口在各类输入条件下的响应正确性，包括参数校验、错误处理、返回格式等。
4. **安全性验证**：确认系统具备完善的身份认证、权限控制、输入过滤机制，能够抵御常见的Web安全攻击（SQL注入、XSS、越权访问等）。
5. **性能基线建立**：建立核心接口的性能基线，确保在高并发场景下系统响应时间和吞吐量满足预期。
6. **兼容性验证**：验证系统在主流浏览器和不同分辨率下的显示与功能正常。
7. **缺陷发现与跟踪**：通过系统测试发现尽可能多的缺陷，并跟踪缺陷修复情况，确保上线前所有严重缺陷均已修复。

## 3. 测试类型

### 3.1 单元测试

- **目标**：验证各个Service方法、工具类方法的逻辑正确性。
- **范围**：核心业务逻辑层，包括订单创建逻辑、钱包扣款逻辑、手续费计算逻辑、库存状态变更逻辑等。
- **工具**：JUnit 5 + Mockito + Spring Boot Test
- **覆盖率要求**：核心业务Service层代码覆盖率不低于80%。

### 3.2 接口测试

- **目标**：验证所有REST API接口的输入输出正确性、参数校验、错误码返回。
- **范围**：后端全部Controller层接口。
- **工具**：Postman / Apifox
- **覆盖要求**：每个接口至少覆盖正常参数、缺失必填参数、非法参数三种场景。

### 3.3 功能测试

- **目标**：从用户视角验证各业务模块的功能是否满足需求。
- **范围**：前端页面交互 + 后端业务逻辑的端到端验证。
- **方法**：黑盒测试，基于等价类划分和边界值分析设计用例。

### 3.4 性能测试

- **目标**：验证系统在高并发场景下的响应时间、吞吐量和稳定性。
- **范围**：市场列表接口、下单接口、搜索接口等高频访问接口。
- **工具**：JMeter
- **指标**：核心接口响应时间 < 500ms（P95），支持至少100并发用户。

### 3.5 安全测试

- **目标**：验证系统的身份认证、权限控制、输入过滤机制的有效性。
- **范围**：JWT认证机制、角色权限体系、SQL注入防护、XSS防护、CSRF防护。
- **方法**：手工渗透测试 + 自动化扫描。

### 3.6 兼容性测试

- **目标**：验证系统在不同浏览器和分辨率下的可用性。
- **范围**：Chrome、Firefox、Edge、Safari等主流浏览器。
- **分辨率**：1920x1080、1366x768、2560x1440。

## 5. 测试策略与方法

### 5.1 测试策略

采用**分层测试策略**，从底层到顶层逐步验证：

```
单元测试 → 接口测试 → 功能测试 → 集成测试 → 性能测试 → 安全测试 → 验收测试
```

1. **单元测试先行**：开发人员在编码阶段同步编写单元测试，确保方法级别逻辑正确。
2. **接口测试跟进**：后端接口开发完成后，立即进行接口测试，验证参数校验和业务逻辑。
3. **功能测试系统化**：前后端联调完成后，进行系统功能测试，覆盖全部业务场景。
4. **非功能测试收尾**：功能测试基本通过后，进行性能测试和安全测试。

### 5.2 测试方法

| 方法 | 说明 | 适用场景 |
|------|------|----------|
| 等价类划分 | 将输入数据划分为有效等价类和无效等价类 | 输入参数校验、表单验证 |
| 边界值分析 | 针对输入范围的边界值进行测试 | 金额范围、分页参数、字符串长度 |
| 场景法 | 按照业务流程场景设计测试用例 | 交易订单流程、钱包充值提现流程 |
| 错误推测法 | 基于经验推测可能出现的错误 | 并发操作、网络异常、数据不一致 |
| 状态迁移测试 | 验证业务实体状态流转的正确性 | 订单状态流转（待付款→已付款→已发货→已完成/已取消） |

### 5.3 缺陷管理

缺陷严重程度分级：

| 等级 | 定义 | 处理要求 |
|------|------|----------|
| 致命(S1) | 系统崩溃、数据丢失、资金异常 | 立即修复，阻塞测试 |
| 严重(S2) | 核心功能不可用、业务逻辑错误 | 24小时内修复 |
| 一般(S3) | 非核心功能异常、界面显示错误 | 3个工作日内修复 |
| 轻微(S4) | 文案错误、UI微调建议 | 下一版本修复 |

## 6. 测试进度安排

按照模块划分测试阶段，各阶段可部分重叠：

| 阶段 | 测试模块 | 测试内容 |
|------|----------|----------|
| 第一阶段 | 基础模块 | 用户登录与认证模块、后台管理模块（饰品/武器类型/品质CRUD） |

| 第五阶段 | 专项测试 | 定时任务测试、安全测试、性能测试 |
| 第六阶段 | 回归与验收 | 全量回归测试、缺陷修复验证、验收测试 |

## 7. 测试通过标准

### 7.1 功能测试通过标准

1. 所有测试用例执行率 ≥ 100%。
2. 测试用例通过率 ≥ 95%。
3. 致命缺陷(S1)：0个未修复。
4. 严重缺陷(S2)：0个未修复。
5. 一般缺陷(S3)：未修复数量 ≤ 5个，且有明确的修复计划。
6. 轻微缺陷(S4)：不影响系统正常使用。

### 7.2 性能测试通过标准

1. 核心接口（市场列表、搜索）响应时间 P95 < 500ms。
2. 下单接口响应时间 P95 < 1000ms。
3. 系统在100并发用户下稳定运行30分钟无异常。
4. 无内存泄漏、无数据库死锁。

### 7.3 安全测试通过标准

1. 无SQL注入漏洞。
2. 无XSS漏洞。
3. 所有受保护接口均需认证，无越权访问漏洞。
4. JWT Token过期机制正常工作。

### 7.4 兼容性测试通过标准

1. Chrome、Firefox、Edge最新版本下功能正常、界面无明显错位。
2. 1920x1080、1366x768分辨率下页面布局正常。
